00Why, and where everything lives

Swaggo puts API truth in comments, so it drifts. doc keeps your handlers as plain http.HandlerFunc factories and attaches metadata to real code: the generic return type carries the schemas, a slice carries extra responses, struct tags carry field detail. The organizing rule — every OpenAPI feature has exactly one home, chosen by its scope:

Field-level → struct tags

Names, required, formats, enums, bounds, examples. Lives on the type: json, jsonschema, query.

Operation-level → Handler fields

Extra status codes, per-code error shapes, response headers, tags, deprecation. Lives in the factory: Responses, Tags, Summary.

API-level → specout.New options

Info block, servers, security schemes, default error codes, component naming. Lives in setup.

How it works, end to end: factories return specout.Handler[Req, Res] wrapping a normal http.HandlerFunc → verb methods record handler metadata at registration → the spec builds once, lazily on first serve: a single walk of the live router resolves full paths, reflection builds the schemas (via invopop/jsonschema) → GET /openapi.json serves it. Zero per-request cost.

01Quick start

Wire it in main, write one factory, register it. That's the whole loop.

Convention

Res defaults to 200 + schema(Res). specout.NoContent (or struct{}) as Res means 204, no body. Path params like {id} are picked up from the route pattern automatically. Everything else is opt-in.

02Registration

As native as Go permits: grouping, middleware scoping, and mounting are pure chi/stdlib, untouched. The one custom thing is the per-route verb call, relocated from r to d so it can carry your types at compile time. d.Adopt(r) is the fallback for routers you don't register yourself.

Verb methods — chi's interface, one subject over

One method per HTTP verb, same names and argument order as chi. Go 1.27's generic methods let them take Handler[Req, Res] directly, so passing a plain http.HandlerFunc is a compile error instead of a silently undocumented route:

Why not plain r.Get?

chi's verb methods take http.HandlerFunc — a defined function type — and a metadata-carrying Handler[Req, Res] is not assignable to it. Interface methods can't take type parameters (the same 1.27 limit as everywhere else), so chi.Router itself can't grow these. A recording wrapper d.Wrap(r) plus a global handler registry would make the calls look native at the cost of hidden global state — exactly what this design refuses. One visible relocated call is the honest floor.

Groups and mounting — 100% native

Registration records only metadata — handler → method, types, responses. Full paths resolve when the spec builds, from a single walk of the live router: chi composes Route/Mount prefixes at match time, invisible at registration time, so trusting the pattern as-passed would put wrong paths in the spec. If you wrap a handler in your own middleware before passing it in, the pointer link falls back to the as-passed pattern, and RequireDocumented flags anything unresolved rather than guessing. Spec-side grouping is OpenAPI tags — the explicit Tags field on the handler.

std http.ServeMux

Why the shim?

http.ServeMux has no public API to enumerate registered routes, so d.Handle records what it needs at registration time — its patterns are always full and unambiguous, no resolution needed. On chi, metadata comes from registration and paths from the build-time walk; middleware never interferes because it wraps at serve time, not in the walk.

03The Handler type

The only thing you touch per endpoint. The closure stays raw std; the struct around it is the metadata.

type Handler[Req, Res any] struct { http.HandlerFunc // embedded — still a plain http.Handler Responses []Response // any code beyond the Res default: 2xx adds success variants, 4xx/5xx override the global error shape (§05) Tags []string // operation tags, for grouping in the spec Summary string OperationID string // optional; derived from method+path when empty Deprecated bool } func (h Handler[Req, Res]) Types() (req, res reflect.Type) type Documented interface { Types() (req, res reflect.Type) }

The Types() method is what makes the type params visible to reflection — it's the reification point. Registration helpers type-assert handlers against Documented; the schema generator never parses source.

05Error responses: global default, per-route shapes

The global envelope is the floor, not the ceiling. Two layers: ErrorType + DefaultErrors in the config define what every operation returns by default, and each route's Responses entries can give any status code a completely different shape — or remove a code that route can't produce.

Layer 1 — the global default

Merge rules

A code not mentioned in Responses keeps the global envelope. An entry with status ≥ 400 replaces the global shape for that code on this route only — nothing global changes. Omit: true removes a global code from this route entirely, and the recorder test (§13) fails if that code ever fires anyway. Distinct types still dedupe into components: SyncConflict is emitted once and $ref'd wherever it appears.

06Write your own helpers

specout ships no decode/respond helpers. Your handlers are raw http.HandlerFunc — read the request the way you want, write the response the way you want. The library only reads what reflection can see: types, tags, route patterns. Most projects write a tiny api package of their own (~40 lines) — that's the pattern the demo uses.

Query parameters

Query params are part of Req, marked with a query tag. Read them with r.URL.Query() in the handler; the spec generator emits them as operation parameters instead of a body.

08The three dials: required, nullable, default

The classic tripwire: these are three orthogonal switches that Go's type system partially conflates. Pick the convention once, stop thinking about it.

DeclarationIn required?Accepts null?
Name stringyesno
Name string json:",omitempty"nono
Name *stringyesyes
Name *string json:",omitempty"noyes
Watch out

"Absent" and "null" are different things in JSON, and Go's *T (nil vs missing key) is the only place it can express the difference. House convention: pointers are nullable, omitempty are optional, default= tags document server-side fallbacks — all three can coexist.

16FAQ

Does this run in production?

The spec is built once at startup — reflection runs, JSON is serialized, and after that /openapi.json serves a fixed byte slice. Zero per-request cost. If even startup cost bothers you, the GO_SPEC_ONLY artifact from CI is byte-identical.

What about middleware wrapping handlers?

The generic registration signatures take Handler[Req, Res] directly, so metadata capture at registration time is guaranteed by the compiler. Wrap with all the middleware you want afterwards — discovery doesn't depend on the call chain. Only d.Adopt(r) (walk fallback) is sensitive to wrapping, which is why the registration helpers are primary.

Why do I have to call d.Get instead of r.Get?

chi's verb methods take http.HandlerFunc — a defined function type — and a metadata-carrying Handler[Req, Res] isn't assignable to it. Interface methods can't take type parameters either, so chi.Router can't grow these itself. A recording wrapper plus a global handler registry would hide the cost in invisible state; d.Get is the same call with the subject moved, and the custom part stays visible.

Why the name specout?

It specs out your handlers — a unique, search-clean token (nothing else on GitHub or pkg.go.dev owns it), self-describing, and short at the call site. The tagline carries the searchable keywords: OpenAPI 3.1 from Go handlers, no comments, verified by your own tests. The instance type is *Generator, so there's no stutter to apologize for.

Why can't it walk my std ServeMux?

http.ServeMux has no public API to enumerate routes — they live in unexported fields. The d.Handle shim records patterns as you register them, which is the same information, obtained reliably.

Circular types (trees, linked structures)?

Handled — schemas that reference themselves resolve through $defs/$ref instead of recursing forever. Go 1.26's self-referential type parameters make some recursive generic shapes (CRTP-style trees) expressible that weren't before; the generated schemas still stay flat via $defs.

Why OpenAPI 3.1 and not 3.0?

3.1's schema dialect is real JSON Schema 2020-12, so the full validation vocabulary (nullable types included) flows through reflection with no translation layer. The version is a config knob if you ever need to emit 3.0 for a stubborn consumer.

What stops the spec from lying about handler behavior?

Three things, in order: the compiler (types must exist), the completeness test (routes must be documented), and the recorder test (codes must match reality). Comments have none of these — that's the whole difference from swaggo.

What if I need something the tags can't express?

JSONSchema() on the type for full schema control, specout.Raw for arbitrary OpenAPI fragments anywhere in the tree. The answer is never "sorry".
